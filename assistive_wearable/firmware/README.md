# Smart Assistive Wearable

## Project summary

This project is an ESP32-C3 wearable prototype for visually impaired users. It uses exactly two physical hardware components:

1. ESP32-C3-DevKitM-1
2. MPU6050 motion sensor

The MPU6050 is the only physical sensor. Blynk IoT, cloud services, extra sensors, speakers, GPS, GSM, cameras, and displays are not used.

The ESP32 processes motion locally, recognizes gestures, estimates activity, detects possible falls, connects to local Wi-Fi, and hosts an HTML dashboard. A phone connected to the same Wi-Fi network opens the dashboard and uses the browser Web Speech API to speak new events through the phone speaker.

This is an engineering prototype, not a medically certified or safety-critical emergency device. MPU6050-only algorithms can produce false positives and false negatives.

## System architecture

```text
          I2C
MPU6050 ────────> ESP32-C3
                    │
                    ├─ 100 Hz sampling
                    ├─ Calibration and filtering
                    ├─ Gesture recognition
                    ├─ Activity recognition
                    ├─ Fall state machine
                    └─ Local HTTP server
                              │ Wi-Fi LAN
                              v
                    Phone browser dashboard
                              │
                              └─ Web Speech API → phone speaker
```

## Hardware wiring

| MPU6050 pin | ESP32-C3 pin | Purpose |
|---|---:|---|
| VCC | 3.3 V | Sensor power |
| GND | GND | Common ground |
| SDA | GPIO5 | I2C data |
| SCL | GPIO4 | I2C clock |
| AD0 | GND or module default | Address selection |

The firmware probes both standard MPU6050 addresses:

- AD0 low: `0x68`
- AD0 high: `0x69`

Use the breakout board's normal I2C pull-ups. Do not apply 5 V unless the specific breakout explicitly supports it.

## Configuration

Application settings are in:

```text
firmware/configs/app_config.h
```

Important settings include:

- I2C SDA: GPIO5
- I2C SCL: GPIO4
- I2C speed: 100 kHz
- Sampling rate: 100 Hz
- Wi-Fi SSID: `Hotspot`
- Wi-Fi password: `security`
- Calibration time: 5 seconds
- Gesture cooldown and duration limits
- Fall impact, jerk, gyro, posture, inactivity, and timeout thresholds

Keep real Wi-Fi credentials private when sharing the project.

## Startup sequence

1. Initialize NVS.
2. Initialize the ESP-IDF I2C master.
3. Probe MPU6050 at `0x68` and `0x69`.
4. Read and validate `WHO_AM_I`.
5. Configure the MPU6050.
6. Collect five seconds of stationary calibration data.
7. Initialize the recognizer and web-state service.
8. Start Wi-Fi station mode and the local HTTP server.
9. Continue sensor processing at 100 Hz.

Keep the wearable still during the calibration message:

```text
Keep the wearable still for 5 seconds
```

## Local web dashboard

After Wi-Fi connects, the serial monitor prints the device address:

```text
Web page available at http://<device-ip>/
```

Open that URL on a phone connected to the same Wi-Fi network. The page includes:

- Current activity
- Last gesture
- Action text
- Integer action code
- Fall status and score
- System state
- Wi-Fi status and IP address
- Accelerometer X/Y/Z
- Gyroscope X/Y/Z
- Tilt angle
- Event history
- Enable Spoken Alerts button

HTTP endpoints:

```text
GET /
GET /api/state
GET /api/history
```

The page polls the JSON state approximately twice per second. Events have monotonically increasing IDs, so the browser speaks each event only once.

### Phone speech behavior

Press **Enable spoken alerts** on the dashboard. Mobile browsers require a user gesture before they permit speech. The phone browser then speaks new important events:

- `Possible fall detected. Are you okay?`
- `Emergency alert cancelled.`
- `Emergency help requested.`
- `Emergency gesture detected.`
- `No response. Emergency state activated.`

Speech is generated by the phone browser, not by the ESP32. The dashboard must remain open and active. Background tabs, browser restrictions, silent mode, and power-saving settings can stop speech. The visible event history remains available when speech is unavailable.

The local server has no authentication and no HTTPS. Use it only on a trusted private Wi-Fi network. Do not expose it to the Internet.

## Gesture mapping

| Gesture | Meaning | Action code |
|---|---|---:|
| LEFT tilt | User is OK during fall response | 1 |
| RIGHT tilt | User needs help | 2 |
| DOUBLE SHAKE | Emergency | 3 |
| FORWARD tilt | Select/confirm | 4 |
| BACKWARD tilt | Cancel/back | 5 |
| SINGLE SHAKE | Repeat/activate | 6 |
| Fall confirmation | Possible fall | 7 |
| Response timeout | No response emergency | 8 |
| No event | None | 0 |

Action values are maintained in the local dashboard state and event history. They are not sent to Blynk because Blynk has been removed.

## Recognition algorithms

### Gesture recognition

The recognizer combines:

- Filtered gravity orientation
- Roll and pitch angle
- Gyroscope magnitude
- Dynamic acceleration
- Gesture duration
- Cooldown timing
- Shake edge detection
- Return from tilt toward neutral

A gesture is accepted only when motion and orientation conditions are satisfied. Cooldown and edge detection prevent repeated actions while the device is held in one position.

### Fall detection

The fall algorithm is state based rather than a single acceleration threshold:

```text
NORMAL
  -> IMPACT CANDIDATE
  -> ORIENTATION/INACTIVITY CHECK
  -> FALL CONFIRMED
  -> WAITING FOR RESPONSE
       LEFT  -> USER OK
       RIGHT -> USER NEEDS HELP
       TIMEOUT -> NO RESPONSE EMERGENCY
```

A candidate combines dynamic acceleration, jerk, gyroscope activity, orientation change, post-impact inactivity, and event duration. Acceleration alone cannot confirm a fall.

### Activity recognition

The initial classifier is explainable and rule based:

- Low motion energy: idle
- Low movement with upright posture: standing
- Moderate repeated motion: walking
- High motion energy: running
- Sustained tilted posture: sitting

Sitting versus standing depends strongly on mounting position and must be tuned with measured data.

## Build, flash, and monitor

Build for ESP32-C3 with ESP-IDF 5.5. Use the project build tools rather than Arduino libraries. After flashing, monitor at 115200 baud and verify:

```text
MPU6050 ready at 0x68
calibration complete
Web page available at http://<device-ip>/
```

If the sensor is not detected, check 3.3 V, GND, GPIO5 SDA, GPIO4 SCL, pull-ups, and AD0.

## Testing checklist

| Test | Expected result |
|---|---|
| Startup still calibration | Bias and gravity values are calculated |
| Normal walking | Walking activity; no fall event |
| Sitting and standing | Heuristic activity; no fall event |
| Running | Running activity; no fall event after tuning |
| LEFT gesture | Action code 1 |
| RIGHT gesture | Action code 2 |
| DOUBLE SHAKE | Action code 3 |
| FORWARD gesture | Action code 4 |
| BACKWARD gesture | Action code 5 |
| Safe simulated fall | Fall event after multiple conditions |
| Fall + LEFT | Alert cancelled; user OK spoken |
| Fall + RIGHT | Help event spoken; emergency remains active |
| Fall + no response | No-response event after timeout |
| Wi-Fi unavailable | Local sensor processing continues |
| Phone speech disabled | Event history remains visible |

Never intentionally drop a person. Use supervised, controlled motion fixtures and collect labeled MPU6050-only data before tuning thresholds for real users.
